# Лекция 1. Часть 1. Обзор предметной области

## Перед лекцией

Отдельной подготовки не требуется.

## Конспект

**Зачем инженеру ИИ/ML нужен Linux**

Курс носит инструментальный характер: цель — не архитектурная теория, а практические навыки работы с Linux на пользовательском уровне, включая базовые сведения о Git. Аргументация строится на рыночных данных: на десктопах доля Linux невелика, но серверный и enterprise-сегмент, а также весь бэкенд интернет-сервисов, платформы автоматизации ML (ClearML, MLflow) и 100% суперкомпьютеров из TOP500 работают на Linux. Даже инженер, не занимающийся системным администрированием, обязан уметь читать логи и 
выполнять базовую диагностику на удалённом сервере — иначе он зависим от инженеров поддержки.

**Аппаратная платформа: архитектура фон Неймана**

Вычислительный узел состоит из модулей: Control Unit и ALU (вместе образуют «процессор»), устройства ввода/вывода, внешнее хранилище и оперативная память. Ключевая идея принстонской (фон-неймановской) архитектуры — единая память для данных и инструкций, что упрощает масштабирование системы. Альтернатива — гарвардская архитектура с раздельной памятью для данных и команд; в чистом виде на десктопах и ноутбуках используется принстонская архитектура, а гарвардский подход применяется локально — в кэш-памяти L1 процессора (раздельные L1i и L1d) для параллельной и более быстрой работы с инструкциями и данными в рамках одного процесса.

**Архитектуры процессоров: CISC vs RISC**

CISC (Intel/AMD, десктопы) — сложные процессоры с богатым набором аппаратно реализованных команд (например, аппаратное шифрование AES), что упрощает написание низкоуровневого кода, но менее энергоэффективно. RISC (ARM, мобильные устройства) — простой, стандартизированный набор команд, выше энергоэффективность, но требуется больше строк кода. Разные архитектуры несовместимы на уровне ассемблера: бинарник, скомпилированный для x86-64, не запустится на ARM без перекомпиляции.

**Зачем нужна операционная система**

ОС как класс ПО решает две исторические задачи: абстрагирование работы с оборудованием (программист не думает, на каком физическом носителе лежит файл) и разделение ресурсов между процессами (не нужно вручную управлять переключением процессора между приложениями). К ним добавляются задачи защиты данных, сетевого взаимодействия, предоставления API (программного интерфейса доступа к функциям системы) и пользовательского интерфейса.

**Кольца защиты и разделение kernel/user space**

Аппаратная защита процессора исторически предполагала 4 кольца защиты (по аналогии со средневековой крепостью — от привилегированного центра к внешним слоям), но на практике используются только два: кольцо 0 (kernel space, максимальные привилегии, работает ОС) и кольцо 3 (user space, ограниченный доступ, только собственная виртуальная память). Падение процесса в user space затрагивает только его; сбой в kernel space может обрушить всю систему.

**Типовая архитектура ОС: слои и интерфейсы**

Любая ОС строится по модульному принципу — декомпозиция на слои, взаимодействующие через стандартизированные интерфейсы. Слои (от аппаратуры к пользователю): аппаратно-зависимые модули (arch/ в исходниках ядра Linux — переписываются полностью при смене процессорной архитектуры), базовые механизмы ядра (аппаратно-независимая логика: переключение контекста процессов, планировщик), менеджеры ресурсов (виртуальная файловая система, память, сеть — абстрагируют доступ к устройствам хранения независимо от физического носителя), интерфейс системных вызовов (в Linux реализуется через glibc) и пользовательские приложения снаружи.

Стабильность интерфейса — ключевое инженерное свойство: внутреннюю реализацию модуля можно полностью переписать без влияния на остальную систему, если сохраняется интерфейс взаимодействия.

**Переносимость ОС между архитектурами**

Модульность обеспечивает переносимость: при переносе на новую архитектуру процессора переписываются только нижние, аппаратно-зависимые слои; пользовательские приложения достаточно перекомпилировать под новую платформу без изменения алгоритмов.

**Классификация ядер: монолит, микроядро, гибрид**

| Тип ядра | Плюсы | Минусы | Примеры |
| :---- | :---- | :---- | :---- |
| Монолитное (полное) | Высокая скорость — все компоненты в одном бинарнике, без накладных расходов на межпроцессное взаимодействие | Выше риск полного отказа системы при сбое любого модуля; для добавления драйвера в «чистом» монолите требуется пересборка и перезагрузка ядра | Классический Unix, ранний Linux |
| Микроядро | Компактный код в kernel space проще проверять и поддерживать; независимая загрузка/выгрузка компонентов | Ниже производительность из\-за межмодульного взаимодействия; дополнительная поверхность атаки на интерфейсы | QNX (система реального времени) |
| Гибридное | Компромисс: модули разделены физически, но работают в kernel space | Более сложная архитектура защиты интерфейсов | Windows, macOS |

**Linux как «модульный монолит»**

Формально Linux — монолитное ядро (весь код работает в kernel space), но с 1995 года поддерживает динамическую загрузку и выгрузку модулей (.ko-файлы) без пересборки ядра — то есть обладает гибкостью, близкой к гибридной архитектуре. Принципиальное отличие от истинно гибридных систем: обращение к загруженному модулю в Linux возможно только через интерфейс системных вызовов, а не напрямую, минуя его.

**Ключевой вывод лекции**

Операционная система — класс программных продуктов, чья основная задача — абстрагирование аппаратуры от приложений и разделение ресурсов между процессами. Слоистая архитектура со стандартизированными интерфейсами между модулями — универсальный инженерный паттерн, который встречается не только в ОС, но и в любых сложных программных системах.

### Уточнения к предыдущей лекции

В паре мест я сознательно упростил или неточно сформулировал детали. Давайте разберем их отдельно.

* **Термин «бит»** я связал с фон Нейманом, но это неточно: сам термин как сокращение "binary digit" предложил Джон Тьюки в 1947 году, а в печатный оборот его ввёл Клод Шеннон в статье 1948 года. Фон Нейман — ключевая фигура в архитектуре вычислительных систем, но не автор этого термина.  
* **Планировщик CFS** я сравнил с «решением системы линейных уравнений» — это была слишком грубая метафора для передачи идеи универсального алгоритма. На деле CFS работает через понятие virtual runtime и красно-чёрное дерево: он выбирает для выполнения процесс с минимальным накопленным виртуальным временем, а дерево обеспечивает быстрый поиск такого процесса.  
* **Автор концепции колец защиты** в устной части прозвучал нечётко. Уточняю: идея аппаратных колец защиты появилась в проекте Multics (MIT, 1965 год) и позже была реализована в архитектуре x86.  
* **Тезис про суперкомпьютеры на Windows до 2015 года** я привёл как общее правило, хотя корректнее говорить о единичных случаях в TOP500, а не о массовой практике — сформулирую точнее при следующем упоминании.

###  Ключевые понятия

#### Аппаратная архитектура

| Термин | Определение для словаря |
| ----- | ----- |
| Принстонская (фон-неймановская) архитектура | Архитектура вычислительного узла с единой памятью для данных и инструкций, что упрощает масштабирование системы. |
| Гарвардская архитектура | Архитектура с раздельной памятью для данных и инструкций; в чистом виде встречается редко, но используется локально в кэш-памяти процессоров (L1i/L1d). |
| Control Unit (устройство управления) | Модуль процессора, отвечающий за диспетчеризацию потоков данных и управление вычислительным процессом. |
| ALU (арифметико-логическое устройство) | Модуль процессора, выполняющий арифметические и логические операции. |
| CISC (Complex Instruction Set Computer) | Архитектура процессора со сложным набором аппаратно реализованных команд (например, Intel/AMD); упрощает низкоуровневое программирование за счёт большего числа транзисторов conclusive+1. |
| RISC (Reduced Instruction Set Computer) | Архитектура процессора с ограниченным набором простых стандартизированных команд (например, ARM); выше энергоэффективность, но требует больше строк кода uvm+2. |

#### Разделение привилегий

| Термин | Определение для словаря |
| ----- | ----- |
| Кольца защиты (protection rings) | Иерархическая система привилегий доступа процесса к ресурсам процессора; на практике используются только кольцо 0 и кольцо 3\. |
| Kernel space | Защищённая область памяти, где выполняется ядро ОС с полным доступом к аппаратуре; доступна только через системные вызовы wikipedia+2. |
| User space | Область памяти, где выполняются пользовательские приложения с ограниченными привилегиями и доступом только к собственной виртуальной памяти wikipedia+2. |

#### Задачи и архитектура ОС

| Термин | Определение для словаря |
| ----- | ----- |
| Абстрагирование оборудования | Одна из двух исторических задач ОС: скрыть от прикладного ПО детали физической реализации устройств (например, тип носителя файла). |
| Разделение ресурсов (диспетчеризация) | Вторая историческая задача ОС: распределение процессорного времени, памяти и других ресурсов между параллельно работающими процессами. |
| API (Application Programming Interface) | Интерфейс, через который приложение вызывает функции доступа к ресурсам системы без знания деталей реализации. |
| Интерфейс взаимодействия (программный интерфейс модуля) | Стандартизированный контракт вызова функции модуля (набор и порядок параметров), обеспечивающий независимость внутренней реализации модуля от остальной системы. |
| Переключение контекста процессов (context switching) | Механизм, при котором процессор последовательно переключается между процессами, создавая эффект параллельного выполнения. |
| Менеджер ресурсов | Слой архитектуры ОС, предоставляющий единый интерфейс доступа к памяти, файловой системе, сети и правам доступа. |
| Виртуальная файловая система (VFS) | Абстракция, позволяющая единообразно работать с файлами независимо от типа физического носителя (диск, флешка, сеть). |
| Машинно-зависимые модули | Нижний слой ядра ОС, взаимодействующий непосредственно с конкретной архитектурой процессора; переписывается полностью при переносе на другую платформу. |
| Аппаратная зависимость / переносимость ОС | Свойство ОС, определяющее объём кода, требующего переписывания при смене процессорной архитектуры; в Linux локализовано в каталоге arch/. |
