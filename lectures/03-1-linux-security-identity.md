# Лекция 3. Часть 1. Безопасность, идентификация и учётные записи пользователей

## Перед лекцией

Отдельной подготовки не требуется.

## Конспект

**Что такое информационная безопасность**

Информационная безопасность (ИБ) — не набор инструментов и не состояние, которого можно один раз достичь, а *непрерывный процесс* обеспечения конфиденциальности, целостности и доступности информации (триада CIA). Помните, в книге Льюиса Кэрролла «Алиса в Зазеркалье» Чёрная Королева говорит: чтобы остаться на месте, нужно бежать, а чтобы попасть в другое место — бежать вдвое быстрее. Так же выглядит и вечное соревнование «брони и снаряда». Новый фактор — большие языковые модели, которые применяют и в технических, и в социальных атаках (в том числе «дистиллированные» версии со снятыми ограничениями).

- **Конфиденциальность** — информация раскрывается только авторизованным субъектам (пользователям, процессам, устройствам).
- **Целостность** — данные не искажены при хранении и передаче, сохраняют полноту и точность. Пример угрозы — частичная подделка данных.
- **Доступность** — в терминах ИБ это не «надёжность работы», а предоставление данных авторизованному субъекту *по его запросу*.

**Четыре вопроса безопасности: идентификация, аутентификация, авторизация, учёт**

| Этап | Вопрос | Пример в Linux |
| :---- | :---- | :---- |
| Идентификация | Кто ты? | Имя `alice` → UID 1001 |
| Аутентификация | Докажи, что это ты | Пароль, SSH-ключ, токен |
| Авторизация | Что тебе можно? | Права `rwx`, ACL, `sudo` |
| Учёт (аудит, accounting) | Что ты сделал? | `last`, `journalctl`, журнал `sudo` |

*Идентификация* — распознавание субъекта по идентификатору. Субъект — пользователь, процесс, запущенный от его имени, или устройство (например, IMEI телефона в сотовой сети). Идентификатор **ничего не доказывает**: он лишь «называет» субъекта. Cookie-файлы в браузере — пример слабой идентификации, их можно украсть. Пароль и ключ идентификаторами не являются — это данные для аутентификации; логин — идентификатор.

*Аутентификация* — проверка подлинности субъекта по предъявленному идентификатору. Участники процесса: субъект, его характеристика (идентификатор плюс предъявляемые данные), механизм аутентификации (в Linux это PAM) и владелец системы аутентификации (хозяин защищаемого ресурса; в нашем случае сама ОС). Специалисты по ИБ никогда не говорят о «100 %»: после аутентификации можно утверждать лишь, что субъект *с высокой вероятностью* тот, за кого себя выдаёт.

*Авторизация* — проверка прав аутентифицированного субъекта на конкретное действие; результат — «разрешить» или «отклонить». Простейший пример из практики: право `x` на скрипт проверяется в момент его запуска.

*Учёт (аудит)* — протоколирование того, что субъект делал в системе; это взгляд «со стороны» на всю цепочку.

**Факторы и виды аутентификации**

| Фактор | Примеры | В Linux |
| :---- | :---- | :---- |
| Знание | Пароль, PIN | Пароль, хеш в `/etc/shadow` |
| Владение | Токен, смарт-карта, телефон с аутентификатором, пропуск | SSH-ключ |
| Свойство субъекта | Отпечаток, лицо, голос | Биометрия через PAM-модули |
| Контекст | Место, время, устройство | Ограничения по IP и времени |

- **Многофакторная аутентификация** — минимум два фактора *разных видов*. Два пароля — это не два фактора. «Пароль + геолокация» — двухфакторная (знание + контекст). «SSH-ключ + пароль на ключ» — владение + знание.
- **Односторонняя** аутентификация — проверяется одна сторона (HTTPS: вы проверяете сайт). **Двусторонняя** — стороны проверяют друг друга (HTTPS + ввод логина и пароля на сайте). В SSH сервер проверяет ключ клиента, а клиент сверяет отпечаток сервера по `~/.ssh/known_hosts`.

**Принципы авторизации**

- **Принцип наименьших привилегий** — субъекту выдаётся ровно столько прав, сколько нужно для задачи. Отсюда правило: постоянная работа под `root` недопустима, это избыточные права.
- **«Запрет по умолчанию»** — разрешено только то, что разрешено явно. Обратная схема («разрешено всё, кроме…») встречается, например, в фильтрации интернета на рабочей сети, но с точки зрения архитектуры безопасности «хорошая система — это диктатура».

**Две модели управления доступом: DAC и MAC**

- **DAC (избирательное управление доступом)** — владелец ресурса сам решает, кому дать доступ. В Linux это права `rwx` и ACL. Именно DAC мы разбираем в лабораторной № 3.
- **MAC (мандатное управление доступом)** — доступ определяет политика системы, владелец ресурса её изменить не может. Субъекту выдаётся мандат (уровень допуска), объектам — уровни секретности. Реализации в Linux: SELinux (в Astra Linux доведён до очень гибкой настройки), AppArmor (по умолчанию включён в Debian). В чистом виде MAC не используется, а комбинируется с DAC.
- Представьте пример MAC: у вас есть допуск к секретному файлу, вы его читаете, но пытаетесь отправить на печать на «открытый» принтер в коридоре. Система запретит: нельзя понижать уровень секретности информации (по сути, правило «no write down» модели Белла — ЛаПадулы).
- **ACL** — это не модель, а *механизм хранения* прав: список записей «кому и что разрешено» для объекта.

**Архитектура безопасности Linux: два «этажа»**

В процессе входа и последующей работы участвуют два пространства:

- **Пользовательское пространство** отвечает на вопрос «кто ты?»: `getty/login`, `sshd`, менеджер входа (GDM, SDDM), библиотека PAM (проверка пароля), библиотека NSS (поиск информации о пользователе), файлы `/etc/passwd`, `/etc/shadow`. Ядро пароль не видит и имени `alice` не знает — ему передаются только числа UID и GID в учётных данных процесса.
- **Ядро** отвечает на вопрос «что можно?»: сравнивает UID, GID и группы процесса с владельцем и правами файла (DAC), учитывает ACL, capabilities и политики LSM (AppArmor/SELinux).

**Поток входа в систему**

1. Программа входа (`login`, `sshd`, графический менеджер) запрашивает логин и пароль.
2. **PAM** аутентифицирует пользователя. По умолчанию используется `pam_unix` (локальные файлы). Для централизованной аутентификации подключаются другие модули: `pam_sss` (SSSD), LDAP, FreeIPA, Active Directory, Google Authenticator (TOTP), FIDO2-ключи, сертификаты на токене. Неудачные попытки пишутся в журнал — это помогает обнаружить подбор пароля.
3. **NSS** (Name Service Switch) формирует «образ» пользователя: UID, основная и дополнительные группы (GID), домашний каталог, оболочка. Источники — локальные файлы, `systemd`, внешний каталог (LDAP, `sss`). NSS — не отдельная служба, а *библиотека*.
4. Управление возвращается PAM: проверяются политики (допустим ли вход на этот хост, не истёк ли пароль, не пора ли его сменить), готовится сессия.
5. Запускается оболочка (например, `bash`) в контексте безопасности пользователя. Далее каждый обращающийся к ресурсам процесс проверяется ядром.

**Что и когда проверяется**

- Аутентификация выполняется **один раз** — при входе. Дочерние процессы наследуют контекст безопасности.
- Авторизация выполняется **постоянно**: при каждом открытии файла (даже если один и тот же файл открыт сто раз). Если владелец системы изменит права, это вступит в силу при следующем открытии.
- Если после входа вас добавили в новую группу, текущая сессия об этом не узнает: нужен повторный вход (`logout/login`) или новая сессия (`su - имя`, `newgrp`), потому что образ пользователя формируется в момент входа.

**Конфигурация PAM**

- Файлы лежат в `/etc/pam.d/<сервис>`, общие части вынесены в `common-auth`, `common-account`, `common-password`, `common-session`.
- Четыре типа правил: `auth` — «кто вы», `account` — «разрешён ли вход сейчас», `password` — смена пароля, `session` — подготовка сессии.
- Флаги управления: `required`, `requisite`, `sufficient`, `optional`.
- Просмотр без комментариев: `grep -v "^#" /etc/pam.d/common-auth`.
- Править конфигурацию лучше через `pam-auth-update`; ошибка в PAM может закрыть вход в систему. Правило администратора: **настраивая доступ к удалённому серверу, всегда держите вторую открытую сессию**.

**Capabilities и LSM**

- *Capabilities* — привилегии `root` разбиты на отдельные права. `root` обходит проверки `rwx` не «по имени», а благодаря `CAP_DAC_OVERRIDE` (на уровне ядра).
- *LSM* (Linux Security Modules) — дополнительный слой политики. В Debian по умолчанию AppArmor; он *только сужает* права.
- Что видит ядро: `grep -E "^(Uid|Gid|Groups|CapEff)" /proc/self/status`, `ls -ln`, `sudo aa-status`.

**Многопользовательская система и диапазоны UID**

Linux изначально многопользовательская: пользователей много, у них разные права, и они работают **одновременно**; параллельно с ними в разных контекстах работают системные службы. В `htop` столбец `USER` показывает контекст, в котором запущен каждый процесс. Пример из лекции: `sshd` работает от `root`, после аутентификации порождает сессию пользователя, внутри которой `su -` снова меняет контекст.

| UID | Назначение |
| :---- | :---- |
| 0 | `root` (фиксированно) |
| 1–999 | Системные пользователи (службы), интерактивный вход обычно запрещён |
| 1000 и выше | Обычные пользователи (первый созданный пользователь получает 1000) |
| 65534 | `nobody` — абстрактный «никто» |

Проверка: `id`, `whoami`, `id alice`.

**Файл `/etc/passwd`**

Читается всеми (иначе утилиты не смогут сопоставить UID и имя). Пример: `artem:x:1000:1000:artem,,,:/home/artem:/bin/bash`.

| Поле | Значение |
| :---- | :---- |
| `artem` | Логин (можно менять — для системы важен UID) |
| `x` | Пароль: хеш хранится в `/etc/shadow` (в старых Unix — прямо здесь) |
| `1000` | UID |
| `1000` | GID основной группы |
| `artem,,,` | GECOS: полное имя, комната, телефоны и прочее |
| `/home/artem` | Домашний каталог |
| `/bin/bash` | Оболочка входа; `nologin` запрещает интерактивный вход (у служб) |

**Файл `/etc/shadow`**

Читать и писать может только `root` (в Debian также читает группа `shadow`). Пример: `artem:$y$j9T$salt$hash:18009:0:120:7:14::`.

| № | Поле |
| :---- | :---- |
| 1 | Имя пользователя |
| 2 | Хеш пароля `$тип$соль$хеш`; `!` или `*` — вход по паролю невозможен |
| 3 | Дата последней смены пароля (дни с 01.01.1970) |
| 4 | Минимальный срок действия (0 — нет ограничения) |
| 5 | Максимальный срок действия (по умолчанию 99999) |
| 6 | Период предупреждения (дни) |
| 7 | Период неактивности после истечения пароля |
| 8 | Срок действия учётной записи (дата в днях) |
| 9 | Зарезервировано |

Читать числа дат вручную не нужно: пользуйтесь `chage -l user`, `chage -M`, `chage -E` и т. д.

**Хеш и соль**

- **Хеш-функция** — односторонне преобразование «текст → строка фиксированной длины». Это не шифрование: обратного алгоритма нет, восстановить пароль можно только перебором. Помните картинку из книги Фила Циммермана с мясорубкой: фарш невозможно провернуть назад.
- Из-за конечной длины хеша разные тексты теоретически могут давать одинаковый хеш (коллизия), но для проверки пароля это не проблема: система сравнивает хеш введённого пароля с сохранённым.
- Зачем хранить хеш, а не пароль: администратор с доступом к `shadow` и злоумышленник, укравший базу, не получают пароли в открытом виде; перебор требует времени, за которое можно заметить утечку и сбросить пароли.
- **Алгоритмы** (префикс в `shadow`): `$y$` — yescrypt (по умолчанию в Debian); `$6$` — SHA-512; `$5$` — SHA-256; `$2y$` — bcrypt; `$1$` — MD5 (устарел, быстро подбирается, есть аналитические методы).
- **Проблема без соли:** одинаковые пароли у разных пользователей дали бы одинаковые хеши; `root` увидел бы это и мог бы войти под другой учёткой, зная пароль «соседа».
- **Соль** — дополнительная строка, которая приписывается к паролю *перед* хешированием. Она хранится открыто (поле между вторым и третьим `$`). Благодаря случайной соли одинаковые пароли дают разные хеши, а заранее вычисленные таблицы (радужные таблицы) становятся бесполезными. Соль может совпасть у двух пользователей — это не страшно; важно, что при разных паролях хеши различны.
- Размер результата хеш-функции не зависит от размера входа (сколько бы данных ни подали).

**Группы пользователей: `/etc/group`**

Пример: `sudo:x:27:artem`. Поля: имя группы, `x` (хеш пароля группы в `/etc/gshadow`), GID, список членов через запятую без пробелов. Файл читается всеми.

- **Основная группа** задаётся GID в `/etc/passwd`; пользователь может *не* значиться в списке членов этой группы в `/etc/group`. Пример: `myuser` имеет GID 1000, но в строке группы `myuser` его имя не указано.
- **Дополнительные группы** перечисляются в `/etc/group` (пример: пользователь `test` добавлен в группу `bluetooth`).
- При создании пользователя обычно создаётся одноимённая основная группа (GID часто совпадает с UID, но не обязан). У пользователя всегда есть хотя бы одна группа.
- **Зачем нужна основная группа сегодня:** при создании файла система записывает владельца-пользователя и подставляет основную группу создателя как группу-владельца. Основные группы разных пользователей могут совпадать — это нормально.
- Проверка: `id`, `groups artem`, `getent group sudo`.

**Утилиты управления пользователями**

| Задача | Debian-обёртка (удобнее) | Низкоуровневая (для скриптов) |
| :---- | :---- | :---- |
| Создать пользователя | `sudo adduser alice` | `useradd -m -s /bin/bash alice` |
| Создать группу | `sudo addgroup project` | `groupadd project` |
| Добавить в группу | `sudo adduser alice project` | `usermod -aG project alice` |
| Без входа по паролю | `sudo adduser --disabled-password alice` | — |
| Удалить | `sudo deluser --remove-home alice` | `userdel -r alice` |

- `adduser` создаёт домашний каталог из шаблона `/etc/skel`, подбирает UID по политике Debian; настройки — `/etc/adduser.conf`. У `useradd` нужны флаги `-m` (создать домашний каталог) и `-s /bin/bash` (оболочка).
- Просмотр и изменение: `id`, `last`, `lastlog`, `who`, `w`, `usermod`, `chage`, `passwd`.
- `--disabled-password` запрещает вход по паролю, но SSH-вход по ключу остаётся возможным. Это удобно для «бастионов», куда ходят только по ключам.

**Безопасная работа с паролями**

- `sudo passwd alice` — интерактивная смена, лучший вариант.
- `echo "alice:новый_пароль" | sudo chpasswd` — пароль попадёт в историю команд; `chpasswd -e` принимает готовый хеш из `stdin`.
- `useradd -p` принимает *хеш* в аргументах: он виден в `ps` и в истории команд. Любой пароль в командной строке остаётся в `~/.bash_history`, может быть виден другим пользователям через `/proc/<pid>/cmdline`.
- Блокировка пароля: `passwd -l alice` или `usermod -L alice`.
- Если пакетное создание пользователей необходимо, его делают скриптом, который читает пароли из файла/памяти и не выводит их в консоль.

### Уточнения и поправки к лекции

- **UID `nobody`.** На лекции прозвучало число 65535. Правильное значение для `nobody` — 65534 (так указано на слайде). Из этого нельзя делать вывод о «16-битном поле»: UID в современных ядрах — 32-битное число.
- **«Хеш можно подобрать через коллизию».** Для взлома украденного хеша злоумышленнику нужно найти *любую* строку с тем же хешем (прообраз). На практике это перебор по словарям и маскам с использованием GPU. Термин «коллизия» корректнее применять к двум *разным* входам с одним хешем — это про целостность и подписи, а не про `shadow`.
- **Соль и радужные таблицы.** Обратите внимание, что соль не только скрывает совпадающие пароли. Есть и вторая, не менее важная роль: соль делает невозможным использование готовых таблиц хешей. Современные алгоритмы (yescrypt, bcrypt) ещё и намеренно медленные.
- **`--disabled-login` и `--disabled-password`.** В демонстрации прозвучали обе опции. На слайде используется `--disabled-password` (запрещает парольный вход); `--disabled-login` отключает ещё и вход любым способом до установки пароля. Для SSH-only доступа нужен именно `--disabled-password`.
- **`passwd --stdin`.** На слайде сказано, что это опция RHEL и в Debian она не работает. В живой демонстрации на лекции мы пробовали эту опцию и предположили, что в Debian 13 её «доработали», но результат остался неочевидным. Для скриптов надёжнее `chpasswd`. Проверьте на своей системе: `passwd --help`.
- **Capabilities «сильнее» прав.** Capabilities не «запрещают поверх rwx». `CAP_DAC_OVERRIDE` — это *исключение*, позволяющее обходить проверку DAC; сужают права как раз LSM (AppArmor, SELinux) и ограничения набора capabilities процесса.
- **Где хранится ACL.** Расширенные ACL хранятся не «в самом inode», а в *расширенных атрибутах* (xattr) файла. Но сами атрибуты привязаны к inode — по смыслу это верно.
- **Основная группа.** Утверждение «нужна только для группы-владельца нового файла» — упрощение: GID также входит в учётные данные процесса и влияет на доступ. Каталог с битом `setgid` (часть 2) переопределяет, какая группа станет владельцем.
- **Авторизация «при каждом открытии».** Строго говоря, права проверяются при `open()` (а также при `exec`, смене прав и т. п.); последующие `read`/`write` по уже открытому дескриптору повторно по `rwx` не проверяются.

### Ключевые понятия

#### Основы ИБ

| Термин | Определение для словаря |
| ----- | ----- |
| Информационная безопасность | Непрерывный процесс обеспечения конфиденциальности, целостности и доступности информации. |
| Конфиденциальность | Свойство информации не раскрываться неавторизованным субъектам. |
| Целостность | Точность и полнота данных, отсутствие искажений при хранении и передаче. |
| Доступность (в ИБ) | Предоставление информации авторизованному субъекту по его запросу. |
| Идентификация | Распознавание субъекта по идентификатору («кто ты?»); сама по себе ничего не доказывает. |
| Аутентификация | Проверка подлинности субъекта по предъявленным данным («докажи»). |
| Авторизация | Проверка прав аутентифицированного субъекта на действие; результат — разрешить или отклонить. |
| Аудит (учёт, accounting) | Протоколирование действий субъекта в системе. |
| Многофакторная аутентификация | Аутентификация по минимум двум факторам *разных видов* (знание, владение, свойство, контекст). |
| Принцип наименьших привилегий | Субъекту выдаются только те права, которые необходимы для задачи. |
| DAC | Избирательное управление доступом: права назначает владелец ресурса (`rwx`, ACL). |
| MAC | Мандатное управление доступом: права определяет политика системы (SELinux, AppArmor). |
| ACL | Список записей «субъект → права» для объекта. |

#### Компоненты безопасности Linux

| Термин | Определение для словаря |
| ----- | ----- |
| PAM | Подключаемые модули аутентификации: единый механизм проверки подлинности для `login`, `sshd`, `sudo`, `su`. |
| NSS | Библиотека Name Service Switch, определяющая источники сведений о пользователях и группах (файлы, LDAP, SSSD). |
| `pam_unix` | Модуль PAM по умолчанию, проверяющий пароль по локальным файлам. |
| Capabilities | Разделение привилегий `root` на отдельные права ядра (например, `CAP_DAC_OVERRIDE`). |
| LSM | Linux Security Modules: слой дополнительных политик (AppArmor, SELinux), только сужающий права. |
| `getent` | Утилита, отвечающая «как система» — из любого источника NSS, в отличие от `grep /etc/passwd`. |

#### Учётные записи

| Термин | Определение для словаря |
| ----- | ----- |
| UID / GID | Числовые идентификаторы пользователя и группы; ядро работает только с ними. |
| `/etc/passwd` | Файл учётных записей, читаемый всеми: логин, UID, GID, GECOS, домашний каталог, оболочка. |
| `/etc/shadow` | Файл хешей паролей и сроков их действия; доступен только `root` (и группе `shadow`). |
| `/etc/group` | Файл групп: имя, GID, список дополнительных членов. |
| Основная группа | Группа, GID которой записан в `/etc/passwd`; становится группой-владельцем новых файлов. |
| Оболочка `nologin` | Программа, запрещающая интерактивный вход (для системных пользователей). |
| Хеш-функция | Необратимое преобразование данных в строку фиксированной длины. |
| Соль | Случайная строка, добавляемая к паролю перед хешированием; хранится открыто. |
| yescrypt (`$y$`) | Алгоритм хеширования паролей по умолчанию в Debian. |
| `/etc/skel` | Шаблон домашнего каталога, копируемый новому пользователю. |
