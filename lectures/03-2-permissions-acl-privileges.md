# Лекция 3. Часть 2. Права доступа, ACL и повышение привилегий

## Перед лекцией

## Конспект

**Повторение: где мы остановились**

В первой части мы разобрали идентификацию, аутентификацию, авторизацию и учёт, модели DAC и MAC, а также связку PAM → NSS → процесс пользователя → проверки ядра. Вторая часть посвящена тому, как ядро принимает решение о доступе к файлам (DAC), как расширить эту модель (ACL) и как безопасно повышать привилегии (`su`, `sudo`). Для проверки идеи «всё есть файл» помните: каталог — тоже файл особого вида, поэтому права на него работают иначе, чем на обычный.

**Чтение вывода `ls -l`**

Пример: `-rwxr-x--- 1 alice project 4096 Nov 3 12:00 run.sh`.

- Первый символ — тип: `-` файл, `d` каталог, `l` символическая ссылка (остальные типы разберём в лекции о файловых системах).
- Дальше три тройки: владелец-пользователь (`rwx`), группа-владелец (`r-x`), все остальные (`---`).
- Здесь владелец `alice`, группа `project`.
- У файла **два владельца**: пользователь и группа. Это *разные* сущности, даже если названия совпадают; формулировку «группа пользователя» из русскоязычных источников нужно понимать именно так.
- Знак `+` в конце строки прав означает наличие ACL.

**Права на обычный файл**

- `r` — читать содержимое.
- `w` — изменять содержимое. Нельзя удалить файл только правом `w` на файл, но можно полностью его обнулить.
- `x` — запускать как программу.
- Удаление и переименование файла определяются правами на **каталог**, а не на сам файл.

**Права на каталог**

| Право | Что даёт на каталоге |
| :---- | :---- |
| `r` | Видеть имена файлов (`ls`) |
| `x` | Заходить (`cd`), обращаться к файлам по имени, видеть атрибуты в `ls -l` |
| `r` без `x` | Видны только имена; атрибуты и содержимое недоступны |
| `w` вместе с `x` | Создавать, удалять и переименовывать файлы в каталоге |
| `w` без `x` | Не работает: без `x` изменять каталог нельзя |

Практические следствия:

- Чтобы добраться до `/srv/project/file.txt`, нужно право `x` на **каждый** промежуточный каталог (`/`, `/srv`, `/srv/project`). Право `r` на них не обязательно: вы не сможете листать каталог и пользоваться автодополнением по `Tab`, но, зная полный путь, файл откроете.
- Без `x` на каталоге ядро откажет, даже если на файле внутри выставлено `rwx`.

**Алгоритм проверки прав**

1. Проверяется `x` на всех промежуточных каталогах пути. Нет — `Permission denied`.
2. Читается inode файла; выбирается **один** класс прав по порядку: владелец → (в расширенном варианте — именованные пользователи и группы по ACL) → группа-владелец → остальные. Срабатывает *первое подходящее*, остальные не проверяются.
3. Проверяется, есть ли в выбранном классе нужное право. Права классов **не суммируются**. Если вы владелец и у владельца права `---`, доступа нет, даже если «все остальные» могут `rwx` (пример `007`: файл открыт всем, кроме владельца и группы).
4. Если права нет, проверяется, не `root` ли это: `root` обходит проверку DAC благодаря capabilities (`CAP_DAC_OVERRIDE`).
5. Если право есть, ядро подключает дополнительные слои: capabilities и политики LSM (AppArmor, SELinux). Они могут отказать, даже если `rwx` разрешает.

Отличие от привычной модели (например, Windows): там эффективные права — это объединение разрешений за вычетом запретов. В классических правах Linux **запретов нет** и классы не складываются.

**Команды изменения прав и владельцев**

- Числовой вид: `r=4`, `w=2`, `x=1`; три цифры — для владельца, группы и остальных. `6` = `110` = `rw-`; `5` = `101` = `r-x`.
- `chmod 644 file` → `rw-r--r--`; `chmod 755 script.sh` → `rwxr-xr-x`.
- Символьный вид: `chmod u+x,g-w,o-rwx file` (u — владелец, g — группа, o — остальные, a — все).
- `sudo chown alice:project file` — сменить и пользователя, и группу; `sudo chgrp project file` — только группу.
- Ключ `-R` применяет изменения ко всему дереву: **проверяйте путь до запуска** (опасный пример — `chown -R` или `chmod -R` на `/`).
- Менять права на свой файл может его владелец; передать файл другому пользователю (`chown`) может только `root`.

**umask: права по умолчанию (расширение лекции)**

Права новых файлов и каталогов задаются не «с нуля», а как *«максимум минус маска»*:

- Максимум для **файла** — `666` (`x` не выдаётся автоматически — это защита от случайного запуска), для **каталога** — `777`.
- `umask` — набор битов, которые из этого максимума **убираются**. Формально: `права = максимум AND NOT umask`.
- `umask 022` (слайд лекции): файлы `644`, каталоги `755`.
- `umask 027`: файлы `640`, каталоги `750` — группа читает, остальным ничего.
- `umask 077`: файлы `600`, каталоги `700` — только владелец.
- `umask 002`: файлы `664`, каталоги `775` — удобно для общих проектных каталогов, когда у каждого пользователя своя одноимённая группа.

Нюансы:

- Это не арифметическое вычитание: для файла при `umask 033` получится `644`, а не `633` (бит `x` в 666 и так нет, а `AND NOT` убирает только присутствующие биты).
- `umask` без аргументов показывает текущее значение; `umask -S` — в символьном виде (`u=rwx,g=rx,o=rx`).
- Значение действует в текущей оболочке и в её потомках. Чтобы сделать его постоянным, пропишите в `~/.bashrc`/`~/.profile` (для пользователя) или в системные настройки (`/etc/login.defs`, `pam_umask`, `/etc/profile`). Конкретное значение по умолчанию зависит от дистрибутива — проверьте командой `umask`.
- Если у каталога есть **default ACL**, маска `umask` для создаваемых в нём объектов не применяется — работают права из default ACL.
- Права, заданные командой `chmod`, `umask` не затрагивает: он работает только в момент создания.

**Особые биты: setuid, setgid, sticky**

| Бит | Число | На файле | На каталоге | Пример |
| :---- | :---- | :---- | :---- | :---- |
| setuid | 4 | Запуск с правами **владельца** файла | Игнорируется | `/usr/bin/passwd` |
| setgid | 2 | Запуск с правами **группы** файла | Новые файлы наследуют группу каталога | Общая папка проекта |
| sticky | 1 | Не используется | Удалять файл может владелец файла, владелец каталога или `root` | `/tmp` |

- В `ls -l` эти биты отображаются как `s` и `t` на месте `x`; если `x` нет, то заглавными: `S`, `T`.
- Задаются четвёртой (старшей) цифрой: `chmod 4755 file`, `chmod 2775 dir`, `chmod 1777 dir`.
- **Классический пример setuid — смена пароля.** `/etc/shadow` может записывать только `root`, а обычный пользователь при этом меняет себе пароль командой `passwd` без `sudo`. Это возможно потому, что владелец `/usr/bin/passwd` — `root`, и на файле стоит `setuid`: программа запускается с правами `root`, а её код не даёт менять чужие записи.
- **Общая папка проекта:** `chmod 2775 /srv/project` и группа-владелец `project`; файлы, создаваемые участниками, автоматически получают группу `project`.
- **`/tmp` с `1777`:** писать может любой, но удалять чужие файлы нельзя — удобно для файлового обмена.
- **Аудит:** `find / -perm -4000 2>/dev/null` показывает все файлы с setuid. Это стандартная проверка на «левые» бинарники (например, setuid на текстовом редакторе — типичный способ оставить себе лазейку). Вторая проверка из лабораторной: в системе должен быть ровно один пользователь с UID 0 — «второй root» с другим именем является классическим бэкдором.
- В Linux `setuid` на *скриптах* (shell-скриптах) ядром игнорируется, он работает только на скомпилированных бинарных файлах.

**POSIX ACL: расширенные права**

Три класса `u/g/o` часто малы: например, нужно дать права конкретному пользователю, не включая его в группу, которая даёт доступ к десятку других файлов.

Подготовка и работа:

- `sudo apt update && sudo apt install acl` — пакет содержит `getfacl` и `setfacl`; проверка: `getfacl --version`.
- `setfacl -m u:bob:rw report.txt` — дать пользователю `bob` права `rw`.
- `setfacl -d -m g:project:rwx /srv/project` — *default ACL* каталога: будет наследоваться новыми файлами.
- `getfacl report.txt` — просмотр; `setfacl -x u:bob report.txt` — удалить запись.
- В `ls -l` появляется `+`, а **группа в выводе показывает маску** (mask).

Что важно знать:

- Владелец и «остальные» сохраняются. Добавляются записи для именованных пользователей и групп.
- Порядок проверки: владелец → именованные пользователи и группы ACL / группа-владелец → остальные. Права разных классов **не суммируются**; запрещающих записей в POSIX ACL нет (в отличие от NTFS).
- **Маска** (`mask::`) ограничивает максимум для именованных записей и группы-владельца. Если маска `r--`, то запись `user:bob:rw-` фактически даст только `r--` (`getfacl` покажет `#effective`). Изменение прав `chmod g=...` при наличии ACL меняет именно маску.
- ACL хранятся в расширенных атрибутах файла (xattr) и требуют поддержки файловой системой (ext4, XFS поддерживают).

**Повышение привилегий: `su` и `sudo`**

Почему не работать под `root`: нет никаких ограничений (ошибка в `rm -rf` ничем не остановится), открытая root-сессия — уязвимость, в логах не видно, кто именно выполнил команду. Поэтому работаем обычным пользователем и повышаем привилегии точечно.

| | `su` | `sudo` |
| :---- | :---- | :---- |
| Чей пароль | Целевого пользователя (`root`) | **Свой** |
| Область | Вся сессия до `exit` | Одна команда |
| Среда | `su -` даёт login-оболочку | `sudo -i`, `sudo -u user` |
| Настройка | Нет | `/etc/sudoers`, `visudo` |
| Журнал | Фиксируется вход | Фиксируется каждая команда |

- `su` без аргументов обращается к `root`; `su alice` — к любому пользователю, при этом спрашивается пароль цели.
- **Минус в `su -` важен**: без него остаются среда, `PATH` и домашний каталог исходного пользователя. Типичное проявление: «command not found» для системных утилит из `/usr/sbin`, потому что в `PATH` у обычного пользователя их нет. С дефисом подтягивается окружение `root`.
- `sudo` — отдельный пакет; в минимальной установке Debian его может не быть. Установка от `root`: `apt install sudo`, затем `usermod -aG sudo user`. Проверка своих прав: `sudo -l`.
- Пароль `sudo` кэшируется на короткое время в рамках сессии (по умолчанию несколько минут, настраивается).
- Группа, дающая доступ к `sudo`: в Debian/Ubuntu — `sudo`, в Red Hat-семействе (CentOS, Fedora) — `wheel` (название происходит от жаргонного *big wheel* — «большая шишка»).
- Корпоративное преимущество: команде администраторов не нужно раздавать пароль `root`; в журнале видно, кто и когда что запускал.

**Файл `/etc/sudoers`**

Формат правила: `кто где = (от_кого) команды`.

- `alice ALL=(ALL:ALL) ALL` — `alice` может всё.
- `%sudo ALL=(ALL:ALL) ALL` — всё группе `sudo` (знак `%` означает группу).
- Редактировать **только** через `visudo` (он проверяет синтаксис; ошибка в `sudoers` может лишить вас `sudo`). Для отдельных правил: `sudo visudo -f /etc/sudoers.d/имя`. Права файла в `sudoers.d` — `0440`; проверка синтаксиса: `sudo visudo -c`.
- **Побеждает последнее подходящее правило**, а не сумма разрешений. Для Debian: члены группы `sudo` получают полный доступ.
- Если вы не можете войти в `sudo`, спасёт обычный `su` с паролем `root` (если он задан).

Примеры «как надо»:

- `alice ALL=(root) /usr/bin/systemctl restart nginx.service` — только эта команда с этими аргументами.
- `%admins ALL=(ALL:ALL) ALL` — вся группа `admins`.
- `backup ALL=(root) NOPASSWD: /usr/local/sbin/run-backup` — без пароля, но только для фиксированного скрипта, который пользователь изменить не может.
- `NOPASSWD: ALL` и `NOPASSWD` для общих утилит вроде `apt` недопустимы: это `root` без пароля.

**Разбор слайда «Как не надо: чёрный список»**

Задача: пользователь `alice` должна чистить логи в `/var/log/myapp`. Неудачная конфигурация:

- `alice ALL=(ALL) ALL, !/bin/rm`
- `alice ALL=(root) /usr/bin/rm /var/log/myapp/*`

Почему это плохо:

- Первое правило разрешает *всё*, включая `sudo bash`; запрет `rm` бессмысленен: в root-оболочке можно запустить что угодно.
- Утилиту легко скопировать: `sudo cp /bin/rm /tmp/x; sudo /tmp/x`.
- Удалять умеют не только `rm`: `find -delete`, `mv`, `unlink`, редакторы.
- Звёздочка в sudoers подставляет любую строку, включая `..` и лишние аргументы: `rm /var/log/myapp/../../etc/passwd`.
- Официальная документация (`man sudoers`) не рекомендует чёрные списки: действует принцип «запрещено всё, что явно не разрешено».

**Правильное решение**

- Вариант 1. Root-скрипт на одно действие `/usr/local/sbin/clean-myapp-logs` (владелец `root:root`, права `0755`): `find /var/log/myapp -type f -name "*.log" -mtime +30 -delete`. В sudoers: `alice ALL=(root) /usr/local/sbin/clean-myapp-logs ""` — пустые кавычки запрещают аргументы. Скрипт пользователь изменить не может.
- Вариант 2 (самый простой и наиболее «человеческий»): выдать `alice` права на каталог логов через группу или ACL (`setfacl -m u:alice:rwx /var/log/myapp`) — без `sudo` вообще.

**Типичные ошибки**

- `chmod 777`: «все» получают запись. На веб-сервере с PHP/Python-приложением это значит, что любой, кто сумеет повлиять на скрипт (например, через уязвимость), может изменить ваши данные. Выдавайте минимально необходимое.
- Постоянная работа под `root`, а не через `sudo`.
- `chmod -R`/`chown -R` без проверки пути.
- Пароль в командной строке: он остаётся в `~/.bash_history`, виден в `ps` и в `/proc/<pid>/cmdline`. Предпочитайте интерактивный ввод или скрипты, читающие пароль из файла и не выводящие его.
- Чёрные списки в `sudoers`; правка `sudoers` в обход `visudo`.
- Правка PAM или SSH на удалённом сервере **без запасной открытой сессии** («примета: пора надевать кроссовки и ехать к консоли»).
- Недостаточные политики паролей и чрезмерные: требование менять пароль каждую неделю и сложные правила приводят к стикерам на мониторе. Для действительно критичных рабочих мест надёжнее аппаратные средства (смарт-карта, токен), а для разумных пользователей — баланс.

**Централизованная аутентификация (взгляд вперёд)**

- На одном сервере локальные `/etc/passwd`/`/etc/shadow` достаточно. На сотнях серверов (виртуалки, ноды Kubernetes, Terraform) раздавать ключи и пароли на каждый хост нельзя.
- Решение: единая система идентификации, к которой Linux подключается как клиент через PAM и NSS (`pam_sss`, `nss_sss`). Логин на любом сервере проверяется центральной системой; один вход работает на всех серверах.
- Примеры: OpenLDAP, Active Directory (Microsoft), Samba, FreeIPA, Keycloak (SSO, интернет-сервисы). Кластеры таких систем размещают в нескольких дата-центрах для отказоустойчивости.
- Изменения групповых прав в центральной системе применяются при следующем входе пользователя (образ пользователя строится в момент входа), если не настроено динамическое получение данных.

**Ключевые команды лекции**

`id`, `whoami`, `groups`, `getent`, `adduser`, `deluser`, `addgroup`, `useradd`, `usermod`, `chage`, `passwd`, `chpasswd`, `ls -l`, `chmod`, `chown`, `chgrp`, `umask`, `getfacl`, `setfacl`, `su`, `sudo`, `sudo -l`, `visudo`, `find / -perm -4000`.

### Уточнения и поправки к лекции

- **«Побеждает последняя строка» или «первая»?** В ходе лекции прозвучали обе формулировки: сначала говорилось про последнее правило, а при разборе слайда с чёрным списком — «используется только первая строка». Корректное правило `sudoers` (оно указано на слайде): *побеждает последнее подходящее правило*. Суть проблемы в разобранном примере не в порядке строк, а в том, что чёрный список обходится (копирование, другие утилиты, `sudo bash`, `..` в аргументах).
- **«`root` — особый пользователь по имени».** Он «особый» из-за UID 0 и capabilities. Любой пользователь с UID 0 обладает теми же правами; поэтому проверка «ровно один UID 0» важна.
- **Исполнение для `root`.** `root` обходит проверки чтения и записи, но для запуска обычного файла ему нужен хотя бы один бит `x` (у файла без бита `x` вообще `root` не запустит его напрямую).
- **Смена владельца.** Кстати, `root` действительно «может стать владельцем любого файла». Это верно, но шире: *менять владельца файла* (`chown`) вправе только процесс с `CAP_CHOWN` (обычно `root`); обычный пользователь может лишь менять группу на одну из своих и права на свои файлы.
- **Sticky bit.** Обратите внимание, что на файлах бит сейчас не работает — это верно для современного Linux. Для каталогов удалить файл могут владелец файла, владелец каталога и `root`.
- **`setgid` на каталоге.** Помните: «владельцем-пользователем» станет автор файла, а группой — группа каталога. Верно, и вложенные каталоги также наследуют бит `setgid`.
- **Где хранятся ACL.** Фраза «знание хранится в inode» — упрощение: ACL лежат в расширенных атрибутах, привязанных к inode (см. часть 1).
- **Вопрос о правах `007`.** На лекции прозвучал вопрос о том, как работает такая маска; ответ — в разделе «Алгоритм проверки прав». Владелец с `---` получает отказ, так как выбирается только его класс. В реальности администраторы так не делают, это учебный пример для запоминания принципа «первое подходящее».
- **Ошибка в схеме на слайде проверки прав** (на лекции мы сами отметили, что схема могла быть нарисована неточно): отказ по `rwx` для `root` не останавливает его — `root` обходит DAC через capabilities; а вот политики LSM (AppArmor/SELinux) действительно могут ограничить даже `root`.
- **Обновление групп без перелогина.** После `usermod -aG` текущая сессия не видит изменений; решение — новый вход или `su - имя`/`newgrp`.

### Ключевые понятия

#### Права доступа

| Термин | Определение для словаря |
| ----- | ----- |
| Класс прав (`u/g/o`) | Одна из трёх групп прав: владелец, группа-владелец, остальные. |
| `r`, `w`, `x` | Права чтения, записи и выполнения (для каталога — просмотр имён, изменение состава, вход и доступ по имени). |
| Числовая запись прав | Запись `r=4`, `w=2`, `x=1`; сумма для каждого класса, например 755. |
| `umask` | Маска битов, исключаемых из максимальных прав (666/777) при создании файла или каталога. |
| `chmod`, `chown`, `chgrp` | Команды смены прав, владельца и группы файла. |
| Порядок проверки (first match) | Ядро выбирает *один* подходящий класс прав и применяет только его; права классов не суммируются. |

#### Расширенные возможности

| Термин | Определение для словаря |
| ----- | ----- |
| setuid | Бит, при котором файл запускается с правами владельца (например, `passwd`). |
| setgid | Для файла — запуск с правами группы; для каталога — наследование группы-владельца новыми файлами. |
| sticky bit | Бит каталога: удалять файлы может только их владелец, владелец каталога или `root` (`/tmp`). |
| POSIX ACL | Расширение прав: отдельные записи для пользователей и групп (`setfacl`, `getfacl`). |
| Маска ACL (mask) | Верхняя граница прав для именованных записей и группы-владельца. |
| Default ACL | ACL каталога, наследуемый новыми объектами внутри него. |

#### Повышение привилегий

| Термин | Определение для словаря |
| ----- | ----- |
| `su` | Переход в сессию другого пользователя с вводом *его* пароля; `su -` загружает его окружение. |
| `sudo` | Выполнение одной команды от имени другого пользователя после ввода *своего* пароля; ведётся журнал. |
| `/etc/sudoers`, `visudo` | Файл правил `sudo` и безопасный редактор с проверкой синтаксиса. |
| `NOPASSWD` | Параметр правила `sudo`, отключающий запрос пароля; допустим только для строго фиксированных команд. |
| Чёрный список (в `sudoers`) | Попытка запретить отдельные команды при общем разрешении; ненадёжна, не рекомендуется. |
| `wheel` / `sudo` (группа) | Группа, члены которой получают права `sudo` (Red Hat / Debian). |
| Централизованная аутентификация | Единая система учётных записей (LDAP, AD, FreeIPA, Keycloak), подключаемая через PAM и NSS. |
